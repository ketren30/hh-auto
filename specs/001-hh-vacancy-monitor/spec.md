# Feature Specification: Мониторинг вакансий hh.ru по пользовательским фильтрам, журналы Markdown и черновики откликов

**Feature Branch**: `001-hh-vacancy-monitor`  
**Created**: 2026-05-01  
**Revised**: 2026-05-01  
**Status**: Draft  

**Input**: приложение для работы с данными пользователя на hh.ru через официальные возможности доступа: вход под учётной записью; **настройка одного или нескольких поисков вакансий через фильтры в приложении** (без опоры на сохранённые поиски hh.ru, если API недоступен); периодический опрос с интервалом *n* минут по каждому включённому поиску; обнаружение новых вакансий относительно предыдущего успешного опроса; **ведение для каждого поиска Markdown-журнала с таблицей вакансий и отметкой об отклике**; генерация черновиков сопроводительных писем по сохранённому резюме и сведениям о вакансии; звуковое оповещение; отклик по одной вакансии за явное подтверждение. Структура письма — три абзаца (должность и источник; мотивация и культура; навыки и благодарность).

## Clarifications

### Session 2026-05-01

- Q: Где хранятся токены/сеанс доступа к hh.ru, текст резюме и учётные параметры для генерации писем? → A: Только локально на устройстве пользователя; без хранения этих данных на сервере приложения разработчика (вариант A).
- Q: Какие источники участвуют в мониторинге и периодическом опросе? → **Обновление**: сохранённые поиски hh.ru (`saved_searches`) для данного приложения/аккаунта **могут быть недоступны** (лимиты API). Основной режим: **профили поиска**, созданные в приложении (набор фильтров); пользователь включает мониторинг **по каждому такому профилю** отдельно; профили без включённого мониторинга не опрашиваются.
- Q: Поведение опроса при неактивной вкладке (приложение открыто)? → A: Опрос продолжается по интервалу *n*, пока открыта вкладка/окно приложения, даже если вкладка не на переднем плане.
- Q: Отправка отклика на вакансию из приложения? → B: Приложение должно уметь отправлять отклик через официально доступные для приложения возможности hh.ru (вариант B).
- Q: Как устроена отправка откликов (одна за раз или пакетно)? → A: Отдельное явное действие и подтверждение на каждую вакансию; пакетная отправка по умолчанию не используется (вариант A).

### Session 2026-05-01 — журналы и фильтры

- Q: Как фиксировать, какие вакансии новые, а какие уже были в выдаче? → A: Приложение сравнивает выдачу с предыдущим успешным снимком по каждому профилю поиска (аналог FR-004); параллельно ведётся **Markdown-журнал на каждый профиль** с таблицей всех когда‑либо учтённых вакансий и колонкой «отправлен ли отклик» (см. [contracts/search-journal-format.md](./contracts/search-journal-format.md)).
- Q: Какие поля минимально нужны у профиля поиска? → A: основной текст запроса; опыт работы; формат занятости (в т.ч. удалёнка и др. — по возможностям API hh.ru); город или регион поиска; список слов/фраз исключений; пользователь может создать **несколько** профилей и мониторить их **одновременно**.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Вход, профили поиска и резюме (Priority: P1)

Пользователь входит в аккаунт hh.ru через OAuth приложения. На отдельной странице создаёт **один или несколько профилей поиска вакансий**, задавая: текст основного поиска; опыт работы; формат (удалённо / офис / гибрид и т.д. — в пределах поддерживаемых параметров официального поиска вакансий); город или регион; слова/фразы исключения (вакансии, где заголовок или краткое описание содержит исключение, отфильтровываются **на стороне приложения** после выдачи API, если отрицательный запрос недоступен в API напрямую). Для каждого профиля пользователь включает или выключает участие в мониторинге; выбор сохраняется локально. Пользователь сохраняет текст резюме для генерации писем.

**Why this priority**: без авторизации и без определённых запросов к выдаче невозможны мониторинг и персонализация писем.

**Independent Test**: вход, создание двух профилей с разными фильтрами, включение монитория только у одного, сохранение резюме — без запуска опроса и без LLM.

**Acceptance Scenarios**:

1. **Given** пользователь не авторизован, **When** он успешно завершает вход, **Then** приложение показывает активную сессию и доступ к настройке поисков.
2. **Given** авторизованный пользователь, **When** он сохраняет профиль поиска со всеми обязательными полями, **Then** профиль появляется в списке и может быть включён в мониторинг.
3. **Given** несколько профилей, **When** пользователь включает мониторинг только для части из них, **Then** только они участвуют в опросе; состояние сохраняется локально.
4. **Given** пользователь задаёт список исключений, **When** выдача по запросу содержит вакансии с этими фразами в заголовке или отображаемом фрагменте описания, **Then** они не попадают в список «кандидатов» для новизны/журнала для этого профиля (политика сравнения без учёта исключённых id в снимке — по решению реализации, но исключённые не должны порождать ложных «новых» для пользователя).
5. **Given** пользователь обновляет текст резюме и сохраняет, **When** запускается следующая генерация письма, **Then** используется новый текст.

---

### User Story 2 — Периодический опрос, новизна и Markdown-журналы (Priority: P2)

Пользователь задаёт интервал *n* минут. Пока открыто окно приложения, приложение с этим интервалом запрашивает выдачу вакансий **по каждому профилю с включённым мониторингом**, используя официальный метод поиска вакансий (например `GET /vacancies` с параметрами, согласованными с документацией hh.ru на этапе реализации). Приложение определяет вакансии, отсутствовавшие в предыдущем успешном снимке для этого профиля. После каждого успешного цикла приложение **обновляет Markdown-журнал** данного профиля: таблица содержит минимум vacancy id, название, работодатель (если есть), ссылку, время первого появления в этом поиске, признак отклика; формат файла — [search-journal-format.md](./contracts/search-journal-format.md). Журнал хранится локально; пользователь может **экспортировать** его как `.md` файл (скачивание браузером). Импорт из файла в следующей итерации спецификации опционален.

**Why this priority**: ядро ценности «не пропустить новые предложения» и аудируемая история по каждому фильтру.

**Independent Test**: два профиля, разные выдачи (или моки); новые id обнаруживаются один раз; журнал обновляется и содержит строку с `applied: нет` для новых; ошибка API не помечает новые вакансии из кэша без успешного запроса.

**Acceptance Scenarios**:

1. **Given** интервал *n*, открыта вкладка и хотя бы один профиль с мониторингом, **When** проходит *n* минут без ошибки, **Then** выполняется запрос выдачи для каждого такого профиля.
2. **Given** успешная выдача, **When** появились id, отсутствовавшие в предыдущем успешном снимке профиля, **Then** они классифицируются как новые для UI и звукового оповещения.
3. **Given** успешный опрос, **When** журнал пересобран, **Then** таблица включает все вакансии, которые приложение учитывает для этого профиля (минимум все когда‑либо виденные после внедрения функции; политика усечения старых строк — не входит в минимальный объём, допускается рост таблицы).
4. **Given** сбой сети или ошибка hh.ru, **Then** пользователь видит понятное сообщение; новые вакансии не объявляются на основе неуспешного ответа.
5. **Given** вкладка не на переднем плане, **When** наступает время опроса, **Then** опрос по-прежнему инициируется (с оговоркой про дросселирование браузера из Edge Cases).

### User Story 3 — Черновики писем, экран, звук и отметка отклика в журнале (Priority: P3)

Для каждой новой вакансии приложение формирует черновик письма по структуре FR-006, показывает редактируемое поле, звук при появлении новых (если включён). Отклик — одно подтверждение на одну вакансию. После исхода отклика, который пользователь считает успешной регистрацией отклика в терминах FR-015, приложение **обновляет колонку отклика** в Markdown-журнале соответствующего профиля поиска для этой вакансии.

**Independent Test**: см. прежние критерии US3 + проверка, что после успешного apply строка в журнале показывает `applied: да` (или эквивалент).

**Acceptance Scenarios**:

1. **Given** новая вакансия и резюме, **When** генерация завершена, **Then** текст соответствует FR-006.
2. **Given** список новых вакансий, **When** пользователь открывает экран, **Then** у каждой есть редактируемое поле черновика (идентификация профиля-источника отображается или фильтрация по профилю — на усмотрение UX).
3. **Given** новые вакансии в цикле, **When** они показаны, **Then** звук воспроизводится при включённой настройке.
4. **Given** подтверждённый отклик и успешный исход по FR-015, **When** журнал сохранён, **Then** для данной `vacancy_id` в журнале профиля отражено наличие отклика (`applied`) и при возможности время отклика.

---

### Edge Cases

- Нет ни одного профиля поиска — показывается пустое состояние с призывом создать профиль.
- Профили есть, но ни у одного не включён мониторинг — опрос не выполняется; сообщение пользователю; звук из опроса не генерируется.
- Истечение авторизации — повторный вход; без успешного запроса новые вакансии не объявляются.
- Очистка локальных данных — профили, журналы и снимки теряются; восстановление только из экспортированных `.md` пользователем, если такая функция появится позже.
- Генерация письма недоступна — ошибка и ручной ввод (как ранее).
- Отклонение отклика hh.ru — сообщение пользователю; журнал не помечает успешный отклик без подтверждения успеха по FR-015.
- Несколько профилей возвращают одну и ту же вакансию — допускается дублирование строк в разных журналах (журнал пер-профиль).
- Очень большой журнал — экспорт и рендер могут быть тяжёлыми; допускается предупреждение в UI или лимит строк в предпросмотре (реализация).
- Минимальный интервал *n* и лимиты hh.ru — соблюдение минимума в приложении и уважение rate limits.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Приложение MUST позволять авторизацию hh.ru и поддерживать сеанс до окончания или выхода.
- **FR-002**: Приложение MUST позволять создавать, редактировать, удалять **профили поиска вакансий** с полями: текст основного поиска; опыт работы; формат занятости (в допустимых для API значениях); город или регион (способ задания — по документации hh.ru: например идентификатор области); список фраз исключения; необязательное пользовательское имя профиля.
- **FR-003**: Пользователь MUST иметь возможность задать интервал опроса *n* (минуты); приложение MUST опрашивать только профили с включённым мониторингом, с интервалом не чаще объявленного минимума.
- **FR-004**: Приложение MUST сравнивать успешную выдачу каждого включённого профиля с предыдущим успешным снимком этого профиля и определять множество новых вакансий (после клиентской фильтрации исключений).
- **FR-005**: Для каждой новой вакансии приложение MUST формировать черновик письма с использованием сохранённого резюме и сведений о вакансии.
- **FR-006**: Черновик MUST соответствовать структуре из прежней версии спецификации (три абзаца: должность и источник; мотивация и культура; навыки/опыт и благодарность; профессиональный тон). Источник в первом абзаце формулируется в контексте hh.ru и **имени профиля поиска / текстового запроса**, если подписка hh.ru не используется.
- **FR-007**: Экран новых вакансий MUST показывать редактируемый черновик на вакансию; изменения сохраняются в состоянии до смены данных или очистки.
- **FR-008**: При появлении новых вакансий в цикле опроса MUST воспроизводиться звук, если пользователь не отключил уведомления.
- **FR-009**: Пользователь MUST иметь возможность хранить и обновлять текст резюме локально.
- **FR-010**: При ошибках сети или hh.ru приложение MUST показывать понятное сообщение и NOT объявлять «новые» вакансии на основе неуспешных ответов.
- **FR-011**: Секреты, резюме, ключи LLM, профили поиска, снимки и содержимое журналов MUST храниться только локально; MUST NOT отправляться для постоянного хранения на сервер разработчика приложения.
- **FR-012**: Пользователь MUST включать/выключать мониторинг **по каждому профилю поиска**; в опросе участвуют только включённые профили; состояние MUST сохраняться локально.
- **FR-013**: Пока окно приложения открыто и мониторинг активен, приложение MUST планировать опросы по интервалу *n* даже при неактивной вкладке; при закрытии окна опрос прекращается.
- **FR-014**: Отклик через hh.ru — одно явное подтверждение на одну вакансию; без массовой отправки одним подтверждением.
- **FR-015**: После попытки отклика MUST показываться однозначный исход (успех / отказ / доп. шаги на hh.ru); ложный успех запрещён.
- **FR-016**: Для **каждого** профиля поиска приложение MUST вести **Markdown-документ** (журнал) с таблицей вакансий и столбцами минимум: идентификатор вакансии, название, работодатель (если есть), ссылка, время первого появления в этом поиске, признак отклика из приложения; формат MUST соответствовать [contracts/search-journal-format.md](./contracts/search-journal-format.md).
- **FR-017**: Приложение MUST предоставлять **экспорт** журнала профиля в файл `.md` (скачивание); хранение «файла» в браузере допускается как строка Markdown в локальном хранилище до экспорта.
- **FR-018**: После успешного отклика по критериям FR-015 приложение MUST обновить журнал соответствующего профиля так, чтобы для затронутой вакансии было отражено наличие отклика.

### Key Entities

- **Пользователь**: сеанс hh.ru и локальные настройки (интервал, звук, LLM).
- **Профиль поиска вакансий**: стабильный локальный id; фильтры (текст, опыт, формат, регион, исключения); флаг мониторинга; необязательное отображаемое имя.
- **Вакансия (элемент выдачи)**: данные из официальной выдачи поиска; привязка к профилю-источнику опроса.
- **Снимок опроса**: последнее успешное множество vacancy id (и при необходимости метаданные) **на профиль**.
- **Markdown-журнал**: одноимённый артефакт на профиль; человекочитаемая таблица + метаданные фильтров.
- **Черновик письма**, **Попытка отклика**: как в прежней версии спецификации.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: После входа пользователь может создать первый профиль поиска и включить мониторинг не более чем за **три минуты** при стабильном соединении (или за документированное время при необходимости загрузки справочников регионов).
- **SC-002**: Интервал опроса — как в прежней спецификации (±15% при активной вкладке; оговорка для фона).
- **SC-003**: Не менее 90% черновиков содержат три абзаца и темы FR-006.
- **SC-004**: Новые вакансии отображаются с черновиками в сроки прежней спецификации при доступности LLM.
- **SC-005**: Звук в течение 2 секунд после готовности уведомления о новых вакансиях.
- **SC-006**: Качество черновиков — как в прежней спецификации.
- **SC-007**: Исход отклика отображается в сроки прежней спецификации.
- **SC-008**: После успешного опроса журнал каждого активного профиля обновляется так, что все включённые в учёт вакансии присутствуют в таблице; экспорт `.md` содержит те же столбцы, что и канонический формат контракта.

## Assumptions

- Используются официальные методы hh.ru для **поиска вакансий** и откликов; конкретные имена query-параметров (`text`, `experience`, `employment`, `schedule`, `area`, …) уточняются по актуальной документации на этапе реализации и отражаются в `docs/hh-api-notes.md`.
- Сохранённые поиски пользователя на hh.ru **не обязаны** быть доступны приложению; интеграция с ними остаётся опциональной и не входит в минимальный объём после данной пересборки спецификации.
- Журналы и профили не синхронизируются между устройствами через сервер разработчика.
- Генерация письма — внешний LLM по ключу пользователя; минимальный интервал опроса не ниже 3 минут при отсутствии иных ограничений hh.ru.
- Мобильные браузеры и офлайн не входят в минимальный объём.
